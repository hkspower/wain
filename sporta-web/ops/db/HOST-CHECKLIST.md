# Database: the host-side checklist, and how to audit the live database

**Status: built, proven on private test instances and fixture trees, NOT run against the live server and
nothing applied.** Every live step goes through the project's job route (a one-shot job on the VPS through the
Hostinger API), after the owner says go. Never SSH, never a PHP endpoint, never CI.

Two read-only jobs answer "how secure is the database":

| Job | File | Answers | Needs |
|---|---|---|---|
| **Database audit** | `ops/db/db-audit.compose.json` (runs `scripts/db-security-audit.mjs`) | accounts, server settings, TLS, logs, limits, character sets, schema, where secrets are kept and whether they look hashed, card-like numbers in free text, old location lines, retention | a database login (the store's own, or an auditor account) |
| **Host audit** | `ops/db/host-audit.compose.json` (runs `ops/db/host-audit.mjs`) | the facts SQL cannot see: is 3306 published, who shares the network, how the container is locked down, who can read the data folder, backups and secret files | read-only mounts of `/docker`, the container runtime files and the volumes |

`npm run test:db-audit` proves both on private instances (insecure and hardened databases; good and bad fixture
hosts), including that each check goes red when it is blinded. The compose files are generated by
`node ops/db/make-audit-jobs.mjs`; the test fails if they drift from the scripts.

## 1. Run the host audit (ONE read-only job)

1. `node ops/db/make-audit-jobs.mjs --check` prints `ok` twice.
2. Through the Hostinger connector, create a project on VM `2058651` named `sporta-dbaudit-host` from
   `ops/db/host-audit.compose.json`. (The first create often leaves the project "not found": create again with the same
   name. See CLAUDE.md, "Probing the live site".)
3. Read the log. It ends with `HOST_AUDIT_DONE fail=N unknown=M pass=K`. Every FAIL line says what it found and what
   would be good. The job prints names, modes, owners, ports, ages and counts: **no environment value, no file content,
   no password**.
4. Delete the project (`vps_docker_delete`). Nothing else was started, nothing written.

What the job mounts, all `:ro`: `/docker`, `/var/lib/docker/containers` (the runtime truth about each container:
ports, capabilities, mounts; its environment is read only to name variables that hold a literal password),
`/var/lib/docker/volumes` (the data directory's mode and owner). It is on the host network with `pid: host` so it can
read `/proc/net/tcp` and connect to the host's own addresses on port 3306. It does **not** mount the Docker socket,
`/etc`, or the root of the host. If the API refuses `pid: host`, delete that line: only `host.runs_as_non_root`
becomes UNKNOWN. If it refuses a mount, the facts that need it say UNKNOWN with the path; they never turn into PASS.

### The facts, and the value that is good

| Fact | What it proves | How it is read | Good value | If it FAILs |
|---|---|---|---|---|
| `host.containers` | the container runtime files are mounted and readable | `/var/lib/docker/containers` at `/h/containers` | readable | the job's mount was refused: every fact below then says UNKNOWN |
| `host.db_container` | the shop's database container is found | `/var/lib/docker/containers/*/config.v2.json`; name `^sporta`, image mariadb/mysql | one running `mariadb` container | pass `--db-name` if it is named differently |
| `host.port_published` | **3306 is not published to the host or the internet** | `hostconfig.json` `PortBindings` and the runtime `NetworkSettings.Ports` (a mapping bound to 127.0.0.1 is allowed) | `PortBindings: {}`: no `ports:` on the database service | delete the `ports:` entry for 3306, recreate the service (a few seconds of downtime: do it at a quiet hour) |
| `host.port_listening` | nothing on the host listens on 3306/3307/33060/5432/27017/6379/11211 beyond loopback | `/proc/net/tcp` and `tcp6`, state `0A` | none, or `127.0.0.1` only | same as above; find the owner with `ss -ltnp` |
| `host.port_reachable` | a real connect to the host's own addresses (public, docker bridges, loopback) on 3306 gets no answer | `--probe`: addresses from `/proc/net/fib_trie`, one TCP connect each, 3 s | `refused` or `timeout` on every address | as above, then also close it in the Hostinger firewall |
| `host.network_mode` | the database is not on the host network | `hostconfig.json` `NetworkMode` | a named network, not `host` or `container:...` | remove `network_mode: host` |
| `host.network_neighbours` | **only the shop shares the database network** (the earlier scan named neighbour sites on the same server); also prints the network's subnet and the account host pattern for it | every running container's `NetworkSettings.Networks` (address and prefix length) | only `apache-sporta-N` (regex `--web-allow`); not the default `bridge` | give the database a network of its own that only the shop container joins; disconnect others: `docker network disconnect sporta-db_default <container>` |
| `host.privileged` | not privileged, no host PID/IPC, no `SYS_ADMIN`/`NET_ADMIN`/`SYS_PTRACE` added | `hostconfig.json` | `Privileged false`, no such capability | remove `privileged: true` / `cap_add` entries |
| `host.cap_drop` | all capabilities dropped | `CapDrop` | `cap_drop: [ALL]`, adding back at most `CHOWN`, `DAC_OVERRIDE`, `FOWNER`, `SETGID`, `SETUID` | add `cap_drop: [ALL]` plus those `cap_add` lines; test on a copy (the image's start-up script needs them) |
| `host.no_new_privileges` | processes cannot gain privilege | `SecurityOpt` | `no-new-privileges:true` | `security_opt: ["no-new-privileges:true"]` |
| `host.readonly_rootfs` | the container's own filesystem is read-only | `ReadonlyRootfs` | `true`, with `tmpfs` for `/tmp` and `/run/mysqld` | `read_only: true` and `tmpfs: [/tmp, /run/mysqld]` (advisory: the data volume stays writable) |
| `host.runs_as_non_root` | the database server is not root | `/proc/<pid>/status` of `mariadbd` (needs `pid: host`); else `Config.User` | uid 999 (`mysql`) | `user: "999:999"` in the service, with the data directory owned by 999 |
| `host.image_pinned` | the image is pinned | `Config.Image` | `mariadb:11.8` or a digest, never `:latest` or untagged | pin it, then upgrade deliberately |
| `host.env_secrets` | no password sits in the container environment (visible to `docker inspect` and to anything with the socket) | variable NAMES from `config.v2.json`; a value is never printed | only `*_FILE` variables; no `MARIADB_ALLOW_EMPTY_ROOT_PASSWORD` | switch to `MARIADB_ROOT_PASSWORD_FILE` with a 0400 file, recreate, then **rotate the root password**: the old one has been in `docker inspect` |
| `host.docker_socket` | **the Docker socket is not mounted into the shop or the database** (it would be root on the host) | `Binds` and `MountPoints` of every container on the database network; a reverse proxy elsewhere is only mentioned | none on the database network | remove the socket mount from the web service |
| `host.data_dir` | the data directory is private and holds only data | stat of `/var/lib/mysql`'s volume; names of top-level files | mode `0700` (or `0750`), owner = the server's uid (999); no world-readable file; no dump, `.sql`, `.gz`, `.bak` or query log inside | `chown 999:999` and `chmod 700` the directory; move dumps out; turn the general log off (`log.general`) |
| `host.backups_dir` | **the backup folder is private** (config-3, config-4 of the live security scan) | stat of `/docker/sporta/backups` and everything to depth 3 | folder `0700` root; every file `0600`; no config copy that holds a key | `chmod 700 /docker/sporta/backups`; `chmod 600` the dumps; delete the old `api-config.php` copies once the changes they preceded are accepted |
| `host.backup_recent` | **a database dump exists and is recent** (the live scan found none) | newest `*.sql`/`*.sql.gz` under the backup folder: age, mode | younger than 36 h, mode 0600 | install the nightly dump from the backup lane (`ops/db`), see `db-backup`; until then this FAILs, which is the true state |
| `host.private_config` | secret and config files are closed to other users | modes and owners of `api-config.php`, `db_name`, `db_user`, `db_pass`, `config/`, `mail/`, `voice/` (nothing is read) | secret files `0400`/`0440`/`0600`; no world-readable entry | `chmod 600 /docker/sporta/private/db_pass` etc. (`voice` was `0755`) |
| `host.tts_cache` | spoken assistant replies are pruned and private | file ages under `private/voice/tts-cache` | oldest under 100 days (the monthly `cron-voice.php prune` keeps 90); folder not world-readable | run the prune; `chmod 700` the folder |
| `host.compose_declared` | the compose files declare no published database port, no socket mount, no literal password | lines of `docker-compose*.yml`/`compose*.yml` under `/docker`, depth 3; values are never printed | none | edit the file named in the finding |
| `host.audit_error` | the audit itself ran to the end (this row appears only when it did not) | an exception inside the script, named by its code or type; no value is printed | the row is absent | UNKNOWN: the facts above it are what the job had; re-run, and read the runtime file the error points at |
| `host.firewall` | the firewall closes 3306 | **not visible from a container** | only 80, 443 and SSH from one owner address are open | read the Hostinger firewall group with the connector; `host.port_reachable` is the practical test |

## 2. Run the database audit

`ops/db/db-audit.compose.json` joins the database network and mounts the store's own config and its three database
secret files, exactly as the project's earlier read-only database jobs do. Create the project, read the log, delete it.
The log is the audit report: one line per check, PASS / FAIL / UNKNOWN, with the finding, and ends with a summary.
Counts and names only: no row value is ever printed (the suite plants canary names, phones, emails, tokens, hashes and a
card number and fails if any appears).

* **Limited verdict (the default, the web account).** It can see the settings, the tables and its own grants, so it
  finds the over-privileged web account, the charset, schema, secrets, card-number and location checks. What it cannot
  see it says: the account tables (anonymous users, empty passwords, `root@%`) are **UNKNOWN**, with the missing
  privilege in the reason. UNKNOWN is never a pass.
* **Full verdict (an auditor account).** For the account checks, other connections and triggers, run it again as a
  short-lived auditor. The account can read the account tables, and so password hashes (the tool never selects them), so
  treat it as sensitive: create it, audit, drop it, in one admin job. The password comes from a root-only file the job
  reads; never type it into chat.

```sql
-- as an administrative account, from a one-shot job. Host = the database network's subnet (the host audit prints it
-- in the host.network_neighbours lines: "database network <name> has subnet ...; the account host for the shop is ...").
CREATE USER 'sporta_audit'@'172.18.0.%' IDENTIFIED BY '<read from a 0400 file by the job>' WITH MAX_USER_CONNECTIONS 2;
-- (with simple_password_check on, as the hardening file sets it, the password needs 24+ characters with a digit, a
--  capital, a small letter and a symbol; the host job prints the host pattern: "account host for the shop is 172.18.%")
GRANT SELECT ON mysql.* TO 'sporta_audit'@'172.18.0.%';                    -- account tables; SHOW GRANTS FOR other accounts
GRANT PROCESS, SHOW DATABASES ON *.* TO 'sporta_audit'@'172.18.0.%';       -- other connections; every schema
GRANT SELECT, SHOW VIEW ON sporta.* TO 'sporta_audit'@'172.18.0.%';        -- tables, views, data checks (counts only)
GRANT TRIGGER ON sporta.* TO 'sporta_audit'@'172.18.0.%';                  -- ONLY to see triggers; it also lets the account CREATE them
-- run:  node db-security-audit.mjs ... --auditor sporta_audit
-- then: DROP USER 'sporta_audit'@'172.18.0.%';
```

Edit the job's `command` to switch credentials: replace `--config /run/sporta-api-config.php` with environment
variables `DB_HOST`, `DB_USER`, `DB_PASSWORD_FILE` (a mounted file), `DB_NAME`, and add `--auditor sporta_audit`.
`--tls` / `--tls-ca FILE` turn on TLS (needed once `require_secure_transport` is on). `--connect-timeout SECONDS` (default 30)
ends the run with exit 2 when the server accepts the connection and then says nothing. `--accept ID` records a decision
to live with a FAIL; it is printed as accepted and never counted as a pass. Exit codes: 0 no FAIL, 1 a FAIL, 2 could not
run (including: the server did not confirm a read-only session).

If the Hostinger API refuses the 52 KB project file, run `node ops/db/make-audit-jobs.mjs --fetch <pushed sha>` and use
its output: the same job, but the script is fetched from the public repo at that commit.

### The fix for each FAIL

`ops/db/AUDIT-FIXES.md` is the owner's table: every check, what its FAIL means, and the command that fixes it. It is
generated from the tool (`node scripts/db-security-audit.mjs --fixes-md`) and the test keeps the two in step. The
server settings it asks for are collected in two files. `ops/db/sporta-db-hardening.cnf` is safe to apply on its own.
`ops/db/sporta-db-tls.cnf` (the certificate lines) is applied **only after** the certificate, key and CA are mounted:
measured on MariaDB 10.11, a server told to use a certificate file that is missing **refuses to start** instead of
running without TLS, so those lines are not in the first file. `npm run test:db-audit` starts a private MariaDB from
both (the audit then finds nothing to fail), another from the first file alone with no certificate on disk (it starts,
and the audit says TLS is not available yet), and proves the second file alone does not start without its files.
Before any live restart, rehearse the same files and mounts on a throwaway container with an empty data directory.

## 3. What the live server will probably show (from earlier scans; NOT measured by this lane)

  earlier scan probed names of other sites against the database network; this job lists exactly who is attached.
* `host.backups_dir` FAIL (folder `0755`, a dump `0644`: config-4) and `host.backup_recent` FAIL (only an October

## 4. Decisions only the owner can make

1. **TLS between the shop and the database.** The PHP opens its connection without TLS (`PDO` options in `store.php`,
   the KNET and T-Pay dropins). `tls.require_secure_transport` FAILs until the PHP connects over TLS; enabling
   `require_secure_transport=ON` first would make every order fail. This needs a PHP change (a patch, reviewed through
   the release gate) and a server certificate kept as a secret file. Not done in this lane.
2. **Binary log (point-in-time recovery).** `sporta-db-hardening.cnf` keeps 14 days of binary logs. They are useful
   after a bad update, but they hold every changed row, personal data included. If a nightly dump is enough, delete the
   three `log_bin` lines (then `log.binlog_pitr` FAILs: record it with `--accept log.binlog_pitr`).
3. **Authenticator seed at rest.** Encrypt `admin_users.totp_secret` with a key kept outside the database (a PHP
   change); the audit passes when every value carries an `enc:` prefix. Or `--accept sec.recoverable_secrets`.
4. **Retention.** The privacy page says only "as long as we need them for accounting and for the returns period".
   Pick a period (the audit takes `--order-retention-days N`) and say it on the page. The page also does not mention the
   optional map-location line stored in the order note: `Privacy.jsx` section 1 under-declares it.
5. **`ONLY_FULL_GROUP_BY`.** The eleven `GROUP BY` queries in `dropin/php-store` all parse under it, but run
   `npm run test:native` against a copy with the mode before the live restart.
6. **Restart rehearsal.** Two lines in these files stop a server from starting at all when the thing they name is missing:
   `secure-file-priv=/var/lib/mysql-files` (the directory must exist: mount an empty read-only one) and, in
   `sporta-db-tls.cnf`, the three certificate paths (measured on 10.11: "Failed to setup SSL ... Aborting"). Every other
   option was started on 10.11, not on the live 11.8, so any option 11.8 renamed or removed would also stop it. Start a
   throwaway container of the live image with the same files and mounts on an EMPTY data directory first; apply the
   hardening file, then (after the certificate is mounted) the TLS file, never both in one step.
7. **MariaDB 11.8 end of life.** The tool lists 2028-06-04 and says the date was not confirmed offline; check the
   vendor's maintenance policy before relying on it.

## 5. What this does not cover

* Whether the Hostinger edge firewall allows 3306 (`host.firewall`): read it with the connector.
* Disk and snapshot encryption on the VPS, SSH configuration (`sshd -T`), IPv6 exposure: host-shell items from the
  live security scan.
* Card numbers or location lines in places the database does not hold: the warehouse mail, the backups, the binary
  logs. The audit counts them in tables; the dump and binary-log copies need the same cleaning by hand.
* Authentication plugins other than `mysql_native_password` (the audit's client cannot sign in with `ed25519`); it says
  so plainly if it meets one.

## 6. Independent review (2026-11-04): what it found and changed

The tool and both jobs were re-run on separate private instances and then attacked. Findings, all fixed in this
directory and `scripts/db-security-audit*.mjs`, each with a test that fails without the fix:

* **The TLS lines could take the database down.** `sporta-db-hardening.cnf` named `ssl_cert` / `ssl_key` / `ssl_ca` and said
  the server would start without TLS if they were missing. Measured on MariaDB 10.11: it refuses to start. The lines are now
  in `sporta-db-tls.cnf`, applied last; the first file alone is proven to start with no certificate on disk.
* **Roles hid privileges.** `SHOW GRANTS FOR <user>` lists only `GRANT role TO user`; an account holding a role with ALL
  PRIVILEGES passed `acct.powerful_privs`. The tool now reads each role's grants (nested roles too) and says UNKNOWN when it
  may not read one.
* **Reach beyond the shop schema passed.** `SELECT/INSERT/UPDATE/DELETE ON *.*`, DML on the `mysql` account tables and
  `REPLICATION SLAVE` (a copy of the binary log) were not flagged for an ordinary account.
* **Netmask hosts passed.** `'x'@'0.0.0.0/0.0.0.0'` (every address) and `'x'@'10.0.0.0/0.0.0.0'` were not wildcard hosts.
* **Card numbers in Arabic-Indic digits, or with dots between groups, were not seen**; a password with punctuation in a
  message, a differently-cased key in a JSON column (JSON columns are case-sensitive `utf8mb4_bin`), and a short
  `maps.app.goo.gl` link were not found.
* **A latin1 column broke the card check** (an Arabic pattern cannot be compared with it); the column is now converted
  first, so one old-build table can no longer turn the whole check into UNKNOWN.
* **"0 columns scanned" was a PASS.** An account that can see no column now gets UNKNOWN from the data checks.
* **A silent server hung the job for ever.** Connect and idle timeouts (`--connect-timeout`, default 30 s).
* **The host audit claimed to print the network subnet and did not**; it now prints it with the account host pattern. It no
  longer dies on one corrupt runtime file or a file that vanishes while it looks, and recognises `MYSQL_PWD`-style names.

Still only the live server can confirm: MariaDB 11.8 behaviour (every option and variable above was started on 10.11), the
sign-in plugin of the real accounts, the real `config.v2.json` layout, and the Hostinger edge firewall.

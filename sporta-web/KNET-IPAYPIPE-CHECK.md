# KNET check: official iPayPipe plug-in vs Sporta's PHP Tranportal code

Date: 2026-11-12. This is a read-only comparison. No repo file was changed, and the vendor jar and dll were never run.

**Reference:** KNET's iPayPipe 1.0 (`com.fss.plugin`), decompiled with CFR. Files cited as `iPayPipe.java`, `iPayTransactionPipe.java`, `ParseResouce.java` and `AESAlgorithm.java` are that decompiled source; they are not in the repo. The .NET `iPayPipe.dll` is an IKVM conversion of the same classes and carries the same string literals.

**Sporta paths:**
- `knet.php`, `pay.php`, `callback.php`, `config.example.php`, `README.md`, `.htaccess`: `sporta-web/dropin/php-knet/`
- `admin.php`, `cron-stock.php`, `store.php`: `sporta-web/dropin/php-store/`
- `cbk.php`: `sporta-web/dropin/php-cbk/`
- `fake-knet-bank.php`, `knet-test.mjs`, `unknown-files-scan.mjs`: `sporta-web/scripts/`
- `set-knet.sh`: `sporta-web/ops/knet/`
- `KNET.md`, `VPS-SCAN-2026-10-31.md`: repo root

## 1. Verdict

- **Crypto and message shape match the plug-in.** Sporta's trandata is the same AES as the plug-in's: AES-128-CBC, with the 16-byte resource key as both key and IV, PKCS5/7 padding and uppercase hex. The output was byte-identical on the computed vectors. Field names, the gateway URL, the response parsing and fail-closed decryption also match.
- **Settlement is stricter than the plug-in's.** The plug-in judges nothing. Sporta pays only on `CAPTURED`, with a matching amount and a payment id present.
- **One wire difference remains (D1).** Sporta URL-encodes the values inside the request trandata. The plug-in sends them raw. Whether KPG decodes them is unproven, so fix it before the first TEST transaction or prove it with that transaction.
- **Nothing is proven to block the test-mode go-live.** Three things could stop it, all before any money moves: D1, the bare-host gateway pin (D3), and getting the credentials only as the encrypted resource file (D4).
- **The one silent money gap is D2.** Nothing asks the bank about a payment whose callback was lost. It does not block go-live.

## 3. Proven matches

These vectors were computed with PHP and openssl only. The "Java way" is openssl with the decompiled settings; the jar was not run.

- **Cipher:** both use AES-128-CBC with PKCS5 = PKCS7 (`AESAlgorithm.java:24`; `knet.php:142, 156`). Key `abcdef0123456789`, plaintext `amt=0.100&` → `65DCA84B9F44F3D9108869E51F776BD8` on both. A 222-byte plaintext in the reference's field order gave byte-identical ciphertext, first block `B33D52A57A876C8C5C29D9ECEB955980`.
- **Key and IV:** both are the resource key's bytes, and there is no fixed IV. `AESAlgorithm.java:22-23, 43-44`; `knet.php:142, 156`. `PGKEYENCDECIVSPC` has 0 hits in the src, the javap listings or the dll (searched as UTF-16LE). With that IV the same block gives `22105FBCD21D2AF9C7BA396B906829DE`, and bytes 0-15 (`id=TESTID001&pas`) come out garbled.
- **Hex case:** uppercase on both sides (`AESAlgorithm.java:33`; `knet.php:146`).
- **Key length:** exactly 16 bytes on both (`AESAlgorithm.java:22-25`; `knet.php:80-85`). Keys of 5, 18 (UTF-8), 24 and 32 bytes are refused.
- **Response hex:** read case-insensitively on both. Malformed input fails closed on both (`AESAlgorithm.java:69-76`, `iPayPipe.java:763-766`; `knet.php:152-159`, `callback.php:64-74`).
- **Decrypt failure:** never settles an order (`iPayPipe.java:759-767`; `callback.php:64-74`; `knet-test.mjs:291-293`).
- **Authenticity:** neither side has a MAC or signature. Authenticity rests on decrypting with the shared key (`AESAlgorithm.java:36-53`; `knet.php:149-161`).
- **Response parsing:** both read the response as a query string, the plug-in's hosted path, not its XML path (`iPayPipe.java:773-914`; `knet.php:172-183`, `callback.php:65`).
- **Response field names:** the same lowercase names on both (`iPayPipe.java:780-901`; `callback.php:76, 86-90, 349-352`). `amt` (`:868-871`; `callback.php:90`), `paymentid` (`:780-783`; `callback.php:88`), `trackid` and `udf5` (`:888-891, 804`; `callback.php:86-87, 120`).
- **Request field names:** the same names and case (`iPayPipe.java:145-146, 185-268`; `pay.php:149-168`). Sporta adds none.
- **Fixed values:** `action=1` (`iPayPipe.java:188-190`; `pay.php:152`) and `currencycode=414` (`:260-262`; `pay.php:154`).
- **udf5:** carries the order id and is echoed back (`iPayPipe.java:212-214, 804-807`; `pay.php:60, 167`; `knet.php:438-442`).
- **Gateway URL:** the same five parameters (`param=paymentInit`, `trandata`, `tranportalId`, `responseURL`, `errorURL`) (`iPayPipe.java:148-150`; `pay.php:194-202`).
- **Credential exposure:** `id` and `password` travel only inside trandata, and `tranportalId` in clear (`iPayPipe.java:145-146, 149`; `pay.php:150-151, 197`). The init log has neither (`pay.php:181-192`).
- **Hand-off:** a browser GET to the built URL, with no server-to-server call at init (`iPayPipe.java:133-158, 1598-1600`; `pay.php:149-202`; `src/lib/checkout.js:114-115`).
- **Paid marking:** there is no inquiry before marking paid on either side. Both trust the decrypted callback (`iPayPipe.java:744-768`; `callback.php:65, 76-80, 275-324`).
- **errorURL leg:** unencrypted and not handled by the plug-in (`iPayPipe.java:773-914`). Sporta logs it and does not change the order (`callback.php:44-62`; `knet-test.mjs:374-378`).
- **Bank identifiers:** kept in order columns or the payment log (`callback.php:98-104, 341-355`).
- **Credential mapping:** the plug-in's four values (id, password, resourceKey, webaddress) map one-to-one onto Sporta's config. The alias has no slot, which is correct (`iPayPipe.java:142-147`; `config.example.php:11-12, 25-27`).
- **Unused plug-in features:** card entry, P2P, KFAST and 3-D Secure fields are rightly unused (`iPayPipe.java:316-345, 352-566`; `pay.php:149-168`).
- **Outbound calls:** Sporta makes no outbound KNET call today. The plug-in's only one is tranPipe (`iPayTransactionPipe.java:37, 43-48`; `pay.php:202`).

**Differences proven harmless:**
- **Field order and trailing `&`:** the order differs and Sporta has no trailing `&` (`iPayPipe.java:185-268`; `knet.php:169`). Only the ciphertext changes.
- **Outer query string:** the order and percent-encoding differ (`iPayPipe.java:148-150`; `pay.php:194-202`). These are standard query parameters, and hex trandata is unaffected.
- **Response decoding:** Sporta URL-decodes response values (`knet.php:180`); the plug-in reads them raw (`iPayPipe.java:776-901`). This has no settlement effect: `NOT+CAPTURED` becomes `NOT CAPTURED`, and neither is `CAPTURED`. Fixing D1 does not require changing this. The fake bank uses this function on the request, so change the two together. Read 3DS/PAReq values raw if they are ever consumed.
- **Odd pairs:** for a value containing `=`, Sporta keeps the part after the first `=` (`knet.php:179`) and the plug-in drops the pair (`iPayPipe.java:778-779`). For `udf1=`, Sporta keeps `''` and the plug-in drops it. KNET's result fields contain neither case.
- **Unused optional fields:** `custid` and `udf6`-`udf20` are optional and unused (`iPayPipe.java:215-259, 266-268`).

## 4. Where Sporta is deliberately stricter

- **Paid rule:** paid only when `CAPTURED`, `paymentid` is present, the amount matches in fils, the method is `knet`, and the order is not cancelled or released. This runs under a row lock, and an order that is already paid is left alone (`callback.php:76-80, 200-242, 252-324`). The plug-in judges nothing (`iPayPipe.java:773-914`). `APPROVED` is refused (`knet-test.mjs:351-357`).
- **Amount:** the amount is compared in fils, and a mismatch is held for review (`callback.php:276-293`; `knet.php:522-530`; `knet-test.mjs:267-280`).
- **Missing payment id:** a `CAPTURED` without `paymentid` goes to review (`MISSING_PAYMENT_ID`, `callback.php:278-281`).
- **Order lookup:** retries are resolved through the bank-echoed `udf5` first (`knet.php:418-459`).
- **Decline words:** only `NOT CAPTURED`, `CANCELED` and `CANCELLED` auto-fail. Any other result that is not `CAPTURED` goes to review as `UNRECOGNIZED_RESULT` (`callback.php:332-338`). If TEST runs show other decline words, add them.
- **Request amount:** `amt` is the server's price as an exact 3-decimal KWD string, and a browser amount is ignored (`knet.php:522-535`; `pay.php:123-131`; `knet-test.mjs:139-141`). The plug-in passes `amt` raw (`iPayPipe.java:185-187`).
- **trackid:** letters and digits only, 1-30 characters, unique per attempt, at most 10 attempts (`pay.php:60-63`; `knet.php:351, 366-401`).
- **Return URLs:** responseURL and errorURL are required and must be HTTPS, and the admin limits the host to sporta.com.kw (`knet.php:92-113`; `admin.php:813-815, 822-823`). `knet_assert_payment_config` does not check the host, so a hand-edited `config.php` can still carry any HTTPS URL.
- **Response hex:** non-hex response data is refused before decryption (`knet.php:152-155`).
- **Key check at save:** the 16-byte resource key is checked when the config is saved or inspected (`admin.php:856`, `preflight.php:343`, `setup-config.php:87`, `selftest.php:78`). This also catches PHP silently truncating a 19-byte key to its first 16 bytes. The plug-in fails only at request time.
- **Config before attempt:** the config is validated before an attempt number is used (`pay.php:134-137`). Three refusals are not logged: a bad track id (`pay.php:60-63`), the rate limit (`pay.php:41-43`, `knet.php:291-297`), and a missing config (`knet.php:41-51`).
- **Tranportal ID:** `set-knet.sh:48` requires digits only; the plug-in treats the ID as an opaque string (`iPayPipe.java:145, 149`). Both candidates, 6261 and 626101, pass.

## 5. Credentials

- **What the bank's file holds.** The plug-in never takes typed credentials. It decrypts the bank's `resource.cgn` with the 3DES key in `keystore.bin`, then reads `<id>`, `<password>`, `<resourceKey>` and `<webaddress>` from `<alias>.xml` (`ParseResouce.java:29-69, 101-106, 136-156, 193-203`; `iPayPipe.java:142-147, 1102-1124`). These are exactly Sporta's four slots: `tranportal_id`, `tranportal_password`, `resource_key`, and `test_url`/`production_url`. The alias only picks which XML is read.
- **Ask for RAW values.** Ask KNET for the RAW values in plaintext, for TEST now and for PRODUCTION later. If only the download arrives, extract the values offline with JDK-only code: JCEKS store and key password `password`, alias `pgkey`, then DESede/ECB twice. Never run the vendor jar. Then delete the download. The keystore password and alias are the same in every copy of the plug-in, so the two files are as sensitive as the plain credentials (D10).
- **Tranportal ID.** The `<id>` tag settles whether it is 6261 or 626101. `set-knet.sh:48` (digits only) passes both, so it cannot tell them apart. Relax the check to letters and digits only if `<id>` turns out to contain letters.
- **Resource key.** It must be exactly 16 bytes on both sides. `set-knet.sh:50` counts bytes, which is correct. `read -r` trims edge whitespace, so a padded key is shortened and then refused, which fails safe. `IFS= read -r` would keep it verbatim.
- **Password.** The raw format cannot carry `&` or `=`. With today's `urlencode`, any character outside `[A-Za-z0-9._-]` is also changed on the wire (D1). Until D1 ships, confirm the production password's character set with the bank. `set-knet.sh` and `knet_assert_payment_config` should refuse `&`, `=` and control characters (D6).
- **webaddress.** It is the authority for the gateway host (bare or `www.`) and for the `/kpg` path (D3).
- **KNET.md.** `KNET.md:206-210` should say the download is encrypted. `KNET.md:199-204, 259-261` ("not interchangeable") is wrong; see section 6.

## 6. Refuted claims

- **"The plug-in silently truncates odd-length hex."** It throws, then hits a NullPointerException at `AESAlgorithm.java:52`, and ends at -1 (`iPayPipe.java:763-766`). It fails closed, as Sporta does.
- **"The plug-in infers key size and could do AES-192/256; Sporta's guard prevents that."** Using the key as the IV forces 16 bytes, so the plug-in only ever does AES-128. Sporta's guard protects against PHP silently truncating or padding the key.
- **"A wrong-length key is rejected by the IvParameterSpec constructor."** It is rejected by `Cipher.init` (`AESAlgorithm.java:25, 46`).
- **"Sporta's response urldecode and request urlencode are a self-consistent pair."** Not in the real flow: the bank writes the response. The only coupling is in the test rig (`fake-knet-bank.php:38`).
- **"Most KPG deployments honour the cleartext copy of responseURL."** Unverified; nothing in this report relies on it.
- **"Every refusal in pay.php is logged."** Three are not (section 4).
- **"An unreachable callback means a silently captured payment."** Overstated. `VPS-SCAN-2026-10-31.md:881` says the bank auto-voids a server notification that gets no `REDIRECT=` reply. A captured payment with a pending order is still possible when the bank only redirects the browser.
- **"decryptAES returns UTF-8."** `new String(bytes)` uses the platform default charset, which is UTF-8 only on JDK 18+ or with `file.encoding=UTF-8`. The result is the same for KNET's ASCII responses.
- **`KNET.md`: "the plug-in's values are not interchangeable" (`KNET.md:199-204, 259-261`).** The resource file holds exactly Sporta's four values, used in the same AES scheme.
- **Docs: "IV `PGKEYENCDECIVSPC`" and "CAPTURED or APPROVED".** Contradicted by the reference and by Sporta's own code (D12).
- **Citation fixes.** `buildHostRequest` is `iPayPipe.java:181-275`, not ~319-345; `316-345` is `performTransactionHTTP`. The `KNET.md` "CAPTURED or APPROVED" line is `:137`, not `:139`.

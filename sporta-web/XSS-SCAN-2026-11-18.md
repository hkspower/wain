## Findings

### F1 (Low) CBK error return writes an unauthenticated string into the order row
- **Where:** `dropin/php-cbk/callback.php:37` (`$errorCode = strtoupper(trim(...$in['ErrorCode']...))`, no pattern, no length cap),
  `:121-123` (`cbk_note_gateway_error(..., $errorCode . ' ' . $meaning)`), `:307-316` (`update orders set cbk_message = ? ... where track_id = ? and payment_status = 'pending'`;
  column `varchar(200)`, `schema.mysql.sql:47`).
- **Source:** the query string of `GET /pay/callback.php`. No signature, no session (the file's own comment says so).
- **Reader:** `payment-records.php:333` returns it as `bank_result` (60 chars) to the admin payment record, drawn by
  `public/sporta-admin-brands.js:15778` with `textContent`; the KNET reconcile CSV (`payment-records.php:676`) quotes it behind the
  formula guard (`payrec_csv_line`, `:697`). Whatever the live compiled Orders screen shows of `cbk_message` is unverified.
- **Payload:** `/pay/callback.php?ErrorCode=<SVG/ONLOAD=...>&PayTrackID=<track id of the attacker's own pending order>` stores
  `<SVG/ONLOAD=...> Unknown gateway error` (ran the same string through `strtoupper` here). It cannot fire now: the add-on and React
  escape, an inline handler has no CSP allowance, and upper-casing breaks every JS identifier. It is still free text planted by a
  stranger into a column the owner reads. The KNET twin was written the other way on purpose
  (`dropin/php-knet/callback.php:49-53`: "It is NOT written to the order: this request is unauthenticated"; `$clip` keeps printable ASCII, 200 chars).
- **Smallest fix:** after line 37, `if (!preg_match('/^TIJ[0-9]{4}$/D', $errorCode)) $errorCode = 'UNKNOWN';` and write only that
  code plus `$meaning`. The `Location` line at `:125` already uses `rawurlencode`.

### F2 (Low) `FILTER_VALIDATE_EMAIL` accepts a quoted local part with `<`, `>`, `/` and `=`
- **Proof (PHP 8.3.6 here):** `filter_var('"<script>alert(1)</script>"@a.bc', FILTER_VALIDATE_EMAIL)` and
  `'"<svg/onload=alert(1)>"@a.bc'` are accepted; anything with a space (`<img src=x onerror=...>`), a bare `<`, CR or LF is refused.
  `a@[127.0.0.1]` (an IP-literal domain) is also accepted. The strict pattern the code already uses for the contact e-mail
  (`store.php:2349-2354`, with the `D` flag) rejects all of them.
- **Where it is the only check, and what it stores:**
  - `store.php:2060-2078` `store_admin_attempt`: a failed `/backends` sign-in with that "address" is written to `admin_activity_log.actor_email`
    and mailed to the owner. **Reachable with no account** (five failures lock the account, but the first row is written). The mail's HTML part escapes it (`store.php:2121-2124`); the plain-text part carries it raw.
  - `support.php:56,62`: `support_tickets.customer_email`. The same function rejects `<` and `>` in name, subject and message (`support.php:18`), so the e-mail is the one field that bypasses the rule.
  - `customer-auth.php:13` (`customer_accounts.email`, after `mb_strtolower`) and `api.php:929` (checkout `account_email`, which creates the account).
- **Sinks in this repo:** none. `grep` finds no `actor_email` or `customer_email` in `src/` or `public/*.js`. The sinks are the live compiled admin
  (Activity log, Support, CRM, Customers), which I could not read.
- **Payload:** `POST ?r=support_create` with `email: "<script>alert(1)</script>"@a.bc`. Fires only if a live screen writes it with `innerHTML`; the CSP blocks inline script anyway.
- **Smallest fix:** one helper `store_email_ok()` = `filter_var(...)` AND the `store.php:2352` pattern, used at the five sites above. It also closes the IP-literal recipient (the invite, existing-account and verification mails go to this address).

### F3 (Low) Two public routes hand back stored values without re-validating them
- **`r=slides` -> `cta_href`:** `api.php:204-221` selects `cta_href` raw. The promo bar's `href` IS re-checked on read (`store.php:2205-2206`), the slide's is not.
  Sink: `src/components/HeroSlider.jsx:733` `<Link to={slide.cta_href}>`. react-router 7.18.5 renders an absolute or protocol-relative target verbatim as
  `<a href>` (`node_modules/react-router/dist/development/chunk-6KYCQHYJ.mjs:1047-1075` `parseToInfo`). React 19.3.1 swaps a `javascript:` href for a throwing stub
  (`react-dom-client.production.js:1583`), so what remains is an off-site button (`//evil.example/login`, `https://...`).
  The write route is strict (`admin.php:2861` -> `store_internal_href`, `store.php:4080-4100`: single leading slash, no `//`, no backslash, 180 chars of `[A-Za-z0-9/_-?=&%.#]`),
  so this needs a direct database write.
- **`r=theme`:** `store.php:2882-2894` returns `settings.theme` as stored (`brand`, `accent`, `canvas`, `radius`); the save route validates (`admin.php:3204` `$hex`). This repo's React never reads it. The live bundle does, and an earlier measurement
  (`test:xss-config` section 8, run on a captured bundle) recorded a client-side `#rrggbb` / radius gate; I did not re-run it. The font library IS re-validated on read (`store.php:2825-2855`).
- **Smallest fix:** apply the `store.php:2206` regex to `cta_href` in the `api.php:204` loop (set `null` when it fails); apply `/^#[0-9a-f]{6}$/i` and the `10|16|24` radius list in `store_theme_with_fonts`.

### auth-1 - Admin sign-out does not end other sessions, contrary to the code comments and NATIVE-BACKEND.md
- **Severity:** medium - **Verdict:** confirmed - **Lens:** auth - **Reporter confidence:** high
- **Where:** `dropin/php-store/admin.php:76`
```php
if ($r === 'logout' && $method === 'POST') {
    ...
    $leaving = store_session_admin();
    if ($leaving !== null) store_admin_event($db, $leaving, 'logout');
    if (store_session_resume()) store_session_end();
    store_out(['ok' => true]);
}
```
- **Scenario:** store.php:975 and NATIVE-BACKEND.md say sign-out, a password reset and an authenticator change 'end every session at once'. Only the last two do: they change the fingerprint that store_session_admin() compares. The logout route calls store_session_end(), which destroys only the current session file. Any other browser or copied cookie keeps working for up to 30 days (7 days idle), and nothing lists or revokes sessions. If a cookie is ever stolen (malware, shared computer, backup of the session dir), the owner clicking 'Sign out' does not help; only a password change does.
- **Fix:** Add a per-admin session epoch (for example admin_users.session_epoch) included in store_admin_fingerprint() and bumped on logout, or offer a separate 'sign out everywhere' that bumps it. At minimum correct the comment and doc so the owner knows to change the password after a suspected theft.
- **Verifier:** Logout route, admin.php:76-88: it calls store_session_admin() only to log the event, then `if (store_session_resume()) store_session_end();`. store_session_end() (store.php:1135-1148) empties $_SESSION, expires the cookie, and calls session_destroy() on the active session. That removes only the session file named by the caller's own cookie.

Nothing in that path touches the credentials that every other session is validated against. store_admin_fingerprint() (store.php:1166) hashes only admin_users.password_hash, totp_enabled and totp_secret. store_session_admin() (store.php:1205-1228) re-checks that fingerprint against $_SESSION['admin_auth_fingerprint'] on each request. A second browser, or a copied cookie, still carries a valid session file and a fingerprint that still matches, so it keeps working until the 30-day absolute or 7-day idle limit. There is no session list, per-admin epoch or revoke route. The only other use of store_session_end() is the expiry and invalid-fingerprint paths.

The documentation says otherwise. The comment at store.php:975-976 says "Sign-out, a password reset and a change to the authenticator still end every session at once (the fingerprint below)". NATIVE-BACKEND.md:265-266 says "sign-out, a password reset or a change to the authenticator ends every session at once". Only the last two change the fingerprint inputs, so the claim is wrong for sign-out.

Scope: store.php and admin.php have no uncommitted edits (git status shows only unrelated css/scripts files). I did not run PHP, because this is a code-reading proof.

Severity: it needs a prior cookie theft or an unattended device. The cookie is HttpOnly and SameSite=Strict, and password change and authenticator change do revoke. So it is a defence-in-depth and misleading-documentation gap. Medium is defensible, and low is also arguable. _Notes:_ The reviewer's description is accurate. The suggested fix is sound: add a session epoch to the fingerprint and bump it on logout or on a separate "sign out everywhere" action. At minimum, correct store.php:975-976 and NATIVE-BACKEND.md:265. This matters because the owner would otherwise believe that clicking Sign out evicts a stolen session.

### money-1 - Browser-chosen track id can equal a victim's KNET/T-Pay retry reference, so the bank callback settles the attacker's order with the victim's money
- **Severity:** medium (reported as high) - **Verdict:** confirmed - **Lens:** money - **Reporter confidence:** high
- **Where:** `dropin/php-knet/knet.php:351`
```php
// knet_resolve_track(): exact match is tried FIRST
$q = knet_pdo($cfg)->prepare('select 1 from orders where track_id = ?');
$q->execute([$ref]);
if ($q->fetchColumn()) return $ref;
// the authenticated udf5 hint is only consulted if no order is literally named $ref
if (preg_match('/^[A-Za-z0-9]{1,30}$/', $orderHint) && knet_attempt_ref_matches_order($ref, $orderHint)) {
    $q->execute([$orderHint]); ...
// api.php:673  track ids are chosen by the browser:
if (!preg_match('/^[A-Za-z0-9]{6,30}$/', $track)) store_fail('invalid_track_id');
```
- **Scenario:** Attempt n>=2 of an order X is sent to the bank as X.'A<n>' (knet_attempt_ref / cbk_attempt_ref), and pay.php deliberately allows repeated starts while the order is pending. api.php?r=order lets the BROWSER pick any track_id matching [A-Za-z0-9]{6,30}, including X.'A2'. Attacker who knows X (it is on the victim's result page, URL, WhatsApp, and in the warehouse e-mail; the CBK callback comment itself says track ids are not secrets) creates their own knet order with track_id = X.'A2' and the same total as X (the total is public: ?r=status&id=X returns amount). The victim retries payment (second pay.php start) and pays: the bank echoes trackid=X.'A2' and udf5=X. knet_resolve_track finds an order literally named X.'A2' and returns it BEFORE looking at udf5, knet_settle_order verifies amount against the attacker's order (equal), and marks THE ATTACKER'S ORDER paid and queues 'ship it'. The victim's order X stays pending and is later released by the sweeper; no review flag is raised. Proven by running the real knet_resolve_track/knet_attempt_ref_matches_order against sqlite: /tmp/claude-0/-home-user-wain/a128f64c-8c94-5bf5-b35a-38b83867e084/scratchpad/resolve_proof.php prints 'SETTLES THE WRONG ORDER'. The same code shape is in cbk_resolve_track (php-cbk/cbk.php:276), so T-Pay and knet_via_cbk are affected too. Needs: knowledge of the victim's track id, a matching total, and the victim starting a second attempt.
- **Fix:** In knet_resolve_track and cbk_resolve_track consult the bank-authenticated hint (udf5 / MerchUdf5) FIRST: if it passes the shape and knet_attempt_ref_matches_order(ref, hint) and that order exists, return the hint, only then fall back to exact match. Additionally refuse client track ids ending in /A[1-9][0-9]*$/ at api.php:673 (or mint track ids on the server). Add a regression to test:knet and test:tpay.
- **Verifier:** The mechanism is real and I could not find a guard that stops it. The only open question is how realistic the preconditions are, so I graded it medium instead of the reviewer's high.

**1. The browser can pick a colliding track id.**
- sporta-web/dropin/php-store/api.php:672-673 accepts any `track_id` matching `/^[A-Za-z0-9]{6,30}$/`.
- I grepped php-store/*.php for any rule rejecting ids that end in `A<digit>`, any use of `pay_attempt`, and any server-minted id. None exists.
- orders.track_id is only `varchar(30) not null unique` (schema.mysql.sql:31). So an attacker can create their own KNET order with `track_id = X.'A2'`. Real ids look like `SP` + base36 (src/lib/attempt.js:19-21), about 18 characters, so `X.'A2'` fits within 30.

**2. The victim's retry sends exactly that reference to the bank.**
- php-knet/pay.php:126 calls `knet_attempt_ref`. For attempt n>=2 (php-knet/knet.php:304-343) it returns `substr(X, 0, 30-len('A2')).'A2'`, which is `X.'A2'` for an id of 28 characters or fewer.
- pay.php:171 sends `udf5 = X`.
- pay.php:90-110 allows repeated starts while the order is pending.
- The storefront reuses the same track id on retry (attempt.js `attemptTrackId`).

**3. The callback resolves to the attacker's order.**
- php-knet/callback.php:93 calls `knet_resolve_track($cfg, $gatewayTrack, udf5)`.
- php-knet/knet.php:355-358 runs `select 1 from orders where track_id = ?` on the echoed reference and returns it immediately if a row exists. The udf5 hint is only read afterwards, at lines 365-368.
- The attacker's `X.'A2'` row exists, so the function returns `X.'A2'`.
- `knet_settle_order` (callback.php:153-) locks `where track_id = ?` on that row and checks only these things:
  - payment_method is knet
  - stored amount equals the captured amount
  - fulfilment_status is not cancelled
  - stock_released is 0
- Nothing compares the resolved order with udf5. udf5 is only passed into the resolver (callback.php:93).
- If the attacker's total equals the victim's, it sets `payment_status='paid'` and calls `store_queue_fulfilment`, which queues the ship-it message. The victim's order X stays pending.

**4. Proof run.**
- I ran `/tmp/claude-0/-home-user-wain/a128f64c-8c94-5bf5-b35a-38b83867e084/scratchpad/resolve_proof.php`. It evals the real `knet_resolve_track`, `knet_attempt_ref_matches_order` and `knet_attempt_ref` from the repo against sqlite.
- Output: `reference sent to bank (attempt 2 of victim): VICTIMTRACK123456A2`, `callback resolves it to order: VICTIMTRACK123456A2`, `SETTLES THE WRONG ORDER (attacker's)`.

**5. T-Pay and knet_via_cbk have the same flaw.** `cbk_resolve_track` (php-cbk/cbk.php:276-296) has the same exact-match-first order, and callback.php:231-232 passes `MerchUdf5` as the hint. php-cbk/callback.php was not re-read in full. Its settlement was assumed to follow the KNET pattern.

**Why not high.**
- The attacker must already know the victim's track id X. It is a roughly 18-character random id, not enumerable. It does appear in the victim's result URL, the /invoice and /track pages, the warehouse e-mail and the bank statement. The realistic attacker is someone who has seen the order id: a family member, an insider, or someone looking at a shared screenshot or link.
- The victim must start a second payment attempt, then pay it, after the attacker's order exists. The attacker can pre-create the order as soon as they know X.
- The attacker's total must equal the victim's to the fil. This is achievable because `?r=status&id=X` returns the amount (api.php:403-412).
- Order creation is rate-limited (20 per 10 minutes, and 1 per minute per client and per phone), which slows pre-creating orders for attempts 2 to 9 but does not prevent it.
- The outcome is a genuine wrong-money result: the victim is charged, the attacker's order ships, and no review flag is raised. Detection is weak.

**Uncommitted edits.** `git status` shows uncommitted changes only in public/sporta-checkout-a11y.*, scripts/admin-save-scan.mjs and scripts/checkout-a11y-test.mjs. The dropin files named in the finding are committed, so the finding applies to HEAD as well as the working tree.

**Fix assessment.** The reviewer's fix is sound. Consult the authenticated udf5 hint first: if `knet_attempt_ref_matches_order(ref, hint)` passes and that order exists, return the hint. Only then fall back to the exact match. Also reject client-chosen track ids ending in `/A[1-9][0-9]*$/` at api.php:673, or mint ids server-side. Apply the same change in `cbk_resolve_track`. _Notes:_ Not run here: a live bank callback or the real MariaDB. Neither is needed, because the code path is deterministic and the sqlite run uses the real resolver functions. I did not check for a second, independent mechanism that would mark an order paid from the bank's echo. Because of the exact-match-first order (php-knet/knet.php:355-358), a legitimate victim paying attempt 1 (reference X, hint X) is unaffected. Only attempt 2 or later is exposed. For orders whose id is longer than 28 characters, `X.'A2'` is truncated by the shortened prefix, so the colliding id the attacker needs is the truncated form, which is still within the allowed 6-30 characters.

### money-5 - order_items.name_en/name_ar are varchar(120) but products accept 160-character names: every order containing such a product fails with HTTP 500 under strict SQL mode
- **Severity:** medium - **Verdict:** confirmed - **Lens:** money - **Reporter confidence:** medium
- **Where:** `dropin/php-store/admin.php:1478` (file has uncommitted edits)
```php
$nameEn = store_text($b['name_en'] ?? null, 'name_en', 1, 160);
$nameAr = store_text($b['name_ar'] ?? null, 'name_ar', 1, 160);
-- itemname.mysql.sql / schema.mysql.sql:693
alter table order_items add column if not exists name_en varchar(120) null ..., name_ar varchar(120) null ...
-- products.name_en varchar(160)
// api.php:900 inserts the full catalogue name: $l['name_en'], $l['name_ar']
```
- **Scenario:** The owner saves a product whose English or Arabic name is 121-160 characters (accepted by product_save). A customer adds it to the cart: store_price_lines copies the full name into the line, api.php:900 inserts it into order_items.name_en varchar(120). MariaDB 10.2.4+ default sql_mode includes STRICT_TRANS_TABLES and the PDO connection sets no sql_mode, so the insert throws 1406 'Data too long'; the catch at api.php:991 rolls back and answers {error:'failed'} 500. Every order for that product fails, with no hint to the owner (the failure is indistinguishable from an outage). Not reproduced against MariaDB (shared rig is off limits); established by reading the schema and handler. Current seed has no name over 90 characters.
- **Fix:** Either limit product names to 120 in product_save/brand paths, or truncate when snapshotting (mb_substr($prod['name_en'], 0, 120) in store_price_lines), or widen the order_items columns to 160 in a migration. Prefer the truncation plus a 120 limit in product_save so history and catalogue agree.
- **Verifier:** Read-only static check; I did not run it against MariaDB, as instructed. No guard sits between the 160-char product name and the 120-char column.

1. The catalogue accepts long names. products.name_en and name_ar are varchar(160) (schema.mysql.sql:18-19). product_save admin.php:1478-1479 calls store_text(..., 1, 160), which only rejects names over 160 (store.php:319-323, mb_strlen). Names of 121-160 characters are therefore valid.
2. The order snapshot column is narrower. order_items.name_en and name_ar are varchar(120) null (itemname.mysql.sql:22-23, repeated at schema.mysql.sql:693-694). The base order_items table does not define them (schema.mysql.sql:66-79).
3. Nothing truncates the name. store_price_lines copies it untruncated: 'name_en' => (string)$prod['name_en'] (store.php:3029-3030). api.php:896-900 inserts $l['name_en'] and $l['name_ar'] as they are. I found no mb_substr or LEFT() on that path.
4. The connection sets no sql_mode. The PDO options at store.php:55-65 are ERRMODE_EXCEPTION, FETCH_ASSOC and EMULATE_PREPARES=false. grep for sql_mode and STRICT across the php-store sources and NATIVE-BACKEND.md found no sql_mode setting. MariaDB 10.2.4+ and the stock Docker image default to STRICT_TRANS_TABLES, so an oversize string raises error 1406 'Data too long'.
5. The exception is not caught gracefully. The insert is inside the order transaction. The catch at api.php:990-992 rolls back, and unless the track id already exists (it does not for a new order) the request ends in a generic failure. The reviewer says this is HTTP 500 {error:'failed'}. I did not trace the tail of the catch, but it is the generic failure path.
6. No other limit rescues it. Arabic characters count by mb_strlen in store_text, so 130 Arabic characters pass the 160 limit and exceed 120. The MariaDB column limit is in characters under utf8mb4, so the overflow is real.

The scenario therefore works as described: any product with a 121-160 character name_en or name_ar makes every order containing it fail.

Why I rate it medium and not higher: it needs the owner to enter an unusually long product name (the reviewer notes the seed has none over 90 characters). The impact is limited to orders for that product, and it is easy to fix. The failure is silent and looks like an outage, which keeps it at medium.

Uncertainty: I could not confirm the live server's sql_mode. A non-strict live mode would silently truncate instead of failing. That is unlikely with a MariaDB Docker image, but it is the one open point.

Uncommitted edits: git status shows no uncommitted edits to admin.php, api.php, store.php, itemname.mysql.sql or schema.mysql.sql. The reviewer's file_has_uncommitted_edits=true is wrong for these files. The only modified files are public/sporta-checkout-a11y.css, public/sporta-checkout-a11y.js and scripts/checkout-a11y-test.mjs.

Fix: truncate with mb_substr(..., 0, 120) at store.php:3029-3030. Also either cap product names at 120 in product_save or widen the order_items columns to 160 in a migration. Widening is better for the history. _Notes:_ Static verification only. Key lines: admin.php:1478-1479, store.php:319-323, store.php:3029-3030, api.php:896-900 and 990-992, itemname.mysql.sql:22-23, schema.mysql.sql:18-19 and 693-694, store.php:55-65. The residual uncertainty is the live sql_mode, which I could not check here.

### robust-1 - Uncaught exceptions and the order route's catch leave no log line at all
- **Severity:** medium (reported as high) - **Verdict:** confirmed - **Lens:** robust - **Reporter confidence:** high
- **Where:** `dropin/php-store/store.php:105`
```php
set_exception_handler(function (Throwable $e): void {
    ...
    store_out(['error' => $isMissingSchema ? 'no_table' : 'failed'], $isMissingSchema ? 503 : 500);
});
// api.php:991
} catch (Throwable $e) {
    if ($db->inTransaction()) $db->rollBack();
    ...
    store_fail('failed', 500);
}
```
- **Scenario:** Any database error, TypeError or config problem on any route ends in this handler, or in a local `catch (Throwable)` that calls store_fail('failed', 500). Neither calls error_log(), and api.php has no error_log() call anywhere. PHP does not log an exception that a user handler handles; I proved it with a snippet (log_errors=1, custom handler, `throw` -> nothing written). So the live image's log_errors=On -> stderr setting (92-sporta-errors.ini) never sees these. This is the failure CLAUDE.md records: the live DB lacked `inventory_version`, every order 500'd for 33 days, and there was no trace. The order catch (api.php:991-1002) is worse than the handler. It turns MySQL 1054/1146 into a bare 500 'failed' instead of the handler's 503 'no_table', so monitoring cannot tell a schema gap from a bug. The same pattern is in admin.php cod_paid, card_settled and sync, which end in `store_fail('failed', 500)` after a bare catch. A missing private-config path (config-path.php throws RuntimeException) also surfaces as an unexplained 'failed'. Impact: the next outage of this kind is again invisible and undiagnosable. store.php and admin.php were in the unreviewed WIP snapshot commits (8bf60016, a403b990) made during the scan; no uncommitted edits remain.
- **Fix:** In the handler and in each local catch, call error_log(sprintf('%s %s code=%s at %s:%d', get_class($e), $e instanceof PDOException ? 'sqlstate' : 'msg', $e instanceof PDOException ? (string)($e->errorInfo[1] ?? '') : '', basename($e->getFile()), $e->getLine())). Keep the PDO message out of the log, because 'Duplicate entry' messages carry emails and track ids. In api.php rethrow after rollback, or map 1054/1146 to the same 503 'no_table', and add a monitor on 5xx from /api/api.php?r=order.
- **Verifier:** The mechanism is real, but "high" is too strong; this is an observability gap, not an exploitable defect or wrong money outcome.

**Handler logs nothing.** store.php:105-120 `set_exception_handler` only computes `$isMissingSchema` and calls `store_out(['error' => ... 'no_table' : 'failed'], 503|500)`. It has no `error_log`. A grep of `dropin/php-store/*.php` shows `error_log` calls only in:
- admin.php:279 and :286 (password reset)
- store.php:556, :1441, :1839, :1843, :2847
- cron-*, seo-*, sitemap-* and customer.php

None of these are in the exception floor, in api.php (zero `error_log`), or in the order catch. I found no `set_error_handler` or shutdown logger covering these routes.

**PHP does not log a handled exception.** I ran this in the scratchpad with `log_errors=1`, an `error_log` file and a handler that echoes "handled", then `throw new RuntimeException('boom')`. The script printed "handled" and the log file stayed empty. So the image's `log_errors=On` setting never sees these failures.

**Order catch (api.php:991-1002).** It matches the finding's quote: on `Throwable` it rolls back, releases the COD lock, re-reads the existing row for the idempotent duplicate-track case, and otherwise calls `store_fail('failed', 500)`. It has no logging. It also never rethrows, so the handler's 1054/1146 to 503 `no_table` mapping is bypassed. A missing column such as `inventory_version` therefore comes back as a bare 500 `failed` on the order route. This matches the 33-day silent outage that CLAUDE.md records.

**Admin catches.** admin.php:1309-1311 (`cod_paid`), :1396-1398 (`card_settled`) and :1894-1896 (`sync`) are all `catch (Throwable $e) { rollBack; store_fail('failed', 500); }` with no log.

**Working-tree state.** `git status` shows only `public/sporta-admin-knet.css` modified, so store.php, api.php and admin.php have no uncommitted edits. The last commits touching store.php are WIP snapshots (8bf60016, a403b990, 66c153a5).

**What I could not verify.** I did not find `92-sporta-errors.ini` in the repo, so the live `log_errors` setting is unverified. It makes no difference, because nothing calls `error_log` on these paths and PHP does not log handled exceptions.

**Severity.** No user-visible wrong outcome follows, and the Apache or Traefik access log still shows the 5xx status. The impact is that a schema or config outage is undiagnosable and indistinguishable from a bug, and monitoring cannot tell it apart. That is a medium (availability and operability) gap, not high.

**Fix.** The reviewer's fix is sound, with one tweak. Log the exception class, the PDO `errorInfo[1]`/SQLSTATE and the file:line, and keep the message out of the log because duplicate-entry messages carry emails. In the order catch, rethrow after the rollback, or map 1054/1146 to the same 503 `no_table` token. _Notes:_ Confidence is high on the code facts and the PHP behaviour. The downgrade to medium is a judgment on impact. The store.php:105 quote and the api.php:991 quote both match the working tree. The admin.php cod_paid, card_settled and sync catches are at lines 1309, 1396 and 1894, not the exact lines the reviewer implied, but they match in content.

### robust-2 - T-Pay / KNET-via-CBK return swallows a failed verification: no log, no retry, order left pending for the sweeper
- **Severity:** medium (reported as high) - **Verdict:** confirmed - **Lens:** robust - **Reporter confidence:** medium
- **Where:** `dropin/php-cbk/callback.php:135`
```php
try {
    $token = cbk_get_access_token($cfg);
    $res   = cbk_get_transaction($cfg, $encrp, $token);
} catch (Throwable $e) {
    header('Location: ' . $return . '?status=error&reason=verify_failed', true, 302);
    exit;
}
if (!is_array($res)) {
    header('Location: ' . $return . '?status=error&reason=no_result', true, 302);
    exit;
}
```
- **Scenario:** A shopper pays at CBK and is returned with ?encrp=. If the Authenticate or GetTransactions call times out (curl 30 s), CBK answers 5xx, or the server IP is momentarily unregistered, the code redirects to the error page. It writes no cbk_log line, stores nothing about the return (not even encrp) and schedules no retry. cbk_verify_by_track() exists but nothing calls it. The order stays 'pending' with the money captured. After stock_hold_minutes (120) cron-stock.php releases the stock and the discount uses. A later capture would be parked for review, but nothing ever re-checks this payment. The shopper was charged, the shop sees an abandoned order, and the log has nothing to reconcile against (the KNET gateway logs every branch). When `knet_via_cbk` is on, this is the whole card path. ### Analyser-style findings

- `dropin/php-store/cron-fulfilment.php:195` - MEDIUM (low likelihood, confidence 0.4). No uncommitted edits. sporta_send_row() opens a transaction (176), takes `select fulfilment_status from orders where id = ? for update` via sporta_lock_order() (178), then calls sporta_send_mail() -> mail() at 195 while that row lock is held, and only commits afterwards. mail() has no timeout of its own. knet/callback.php:170 and cbk/callback.php:321 take `for update` on the same orders row to settle a payment. If the relay or msmtp stalls while a callback for that order arrives, the callback waits innodb_lock_wait_timeout (50 s default), its catch returns state=review/database_write_failed, the order stays payment_status='pending' even though the bank captured the money, and cron-stock.php can later cancel a pending knet/tpay order once the hold has passed and put the stock back. The code comments document holding the lock through the mail ('a mail is one sendmail call, so the wait is short') but not this failure case. Fix: give msmtp or sendmail a hard `timeout` (about 15 s). Better, claim the row with a lease, commit, send, then record the result in a second short transaction; or set `innodb_lock_wait_timeout` low in the callbacks and make a lock timeout leave the order retryable rather than silently pending.
- `dropin/php-store/api.php:98` - LOW (confidence high, proven). No uncommitted edits. `$r = $_GET['r'] ?? ''` (line 24) is never type-checked, so `GET /api/api.php?r[]=x` reaches `array_key_exists($r, $STORE_LIMITS)` and throws TypeError. Verified with `php -r` under strict_types: array_key_exists(array, array) throws TypeError. The set_exception_handler in store.php turns it into HTTP 500 {"error":"failed"} BEFORE any store_throttle() call, after store_db() has already opened a connection at line 25. A scanner can therefore produce unthrottled 500s (noise for 5xx alerting) at the cost of a DB connection each. Fix: `$r = is_string($_GET['r'] ?? null) ? $_GET['r'] : '';` at api.php:24, and the same at admin.php:19 for symmetry (admin only compares with ===, so it is not affected today).
- `dropin/php-store/assistant.php:3397` - LOW (confidence high on the facts, impact limited). No uncommitted edits. cron_key plays three roles: the URL secret for the legacy HTTP crons (cron-auth.php:18, cron-voice.php:80, cron-whatsapp.php:41 all read `?key=`, which lands in Apache/Traefik access logs and Referer), the setup-admin.php key, and the HMAC key of every TTS signature (assistant_speech_sig, used by api.php:497 `?r=say`). - `dropin/php-store/seo-runtime.php:5` - LOW (confidence 0.5, depends on the live php.ini which is not in the repo). Mixed clocks for paid_at: admin.php:1302 (admin marks an order paid) and 1371, cron-fulfilment.php:197 and cron-whatsapp.php:86 write PHP-local `date('Y-m-d H:i:s')`, while knet/callback.php:272, cbk/callback.php:365 and store.php:2146/2260 write `gmdate(...)`.

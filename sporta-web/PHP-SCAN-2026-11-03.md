Verifiers lowered 1 high report to medium, 9 medium reports to low and 1 low report to info; none was raised.

**Five things to know first**

1. **Nothing critical or high, and the injection surface is clean.** No finding allows remote code execution, account takeover or a data breach without preconditions. All 30 string-built SQL statements were read (0 injectable); there is no `eval`, `unserialize`, `extract`, shell call from request data, upload sink other than the admin photo route, or non-constant-time secret compare.
2. **One real money-path defect: M1.** A shopper can name their own order so that it collides with the retry reference of someone else's card payment. If that person retries and pays, the bank's callback marks the shopper's order paid and the victim's order stays unpaid. It needs the victim's order number, an equal total and a second payment attempt, but nothing flags it afterwards. Fix is a small reorder in the two callback resolvers (KNET and T-Pay).
3. **A product name of 121 to 160 characters makes every order containing it fail (M3).** The admin accepts 160, the order-line column holds 120; on strict MariaDB the order returns a generic 500 that looks like an outage.
4. **Admin "Sign out" only ends that one browser (M2).** The code comment and `NATIVE-BACKEND.md` say it ends every session. After a suspected stolen cookie, change the password (that does revoke everything).
5. **Money outcomes the shop cannot see (L1 to L3):** a second bank capture on an already-paid order is dropped without a trace (L2); a card order parked in "review" and then cancelled never returns its stock or its single-use code (L3); and KNET is hidden at checkout in the planned one-setup mode unless Tranportal credentials still exist (L1), which becomes a medium the day the merged KNET/CBK release ships.

### 3.1 Medium (3)

**M1 · money-1 · A browser-chosen track id can equal another order's retry reference, so the bank callback settles the wrong order**
- Where: `php-knet/knet.php:351-368` (`knet_resolve_track`), `php-cbk/cbk.php:276-296` (`cbk_resolve_track`), `api.php:672-673` (track id taken from the browser). WIP file: no.
- Found by: money. Verifier: confirmed, **medium** (reported high).
- Scenario: attempt n of order X reaches the bank as `X` + `A<n>` for n of 2 or more, and `pay.php` allows repeated starts while pending. `api.php` accepts any `track_id` matching `[A-Za-z0-9]{6,30}`, and the order total is public via `?r=status`. An attacker who knows victim order X creates an order named `X`+`A2` with the same total. When the victim retries and pays, the callback looks for an order literally named `X`+`A2` first (exact match before the bank-authenticated `udf5` hint), finds the attacker's, passes the amount check, marks it paid and queues "ship it". The victim's order stays pending and is later released by the sweeper; no review flag is raised. Attempt 1 is unaffected. Same shape in T-Pay and `knet_via_cbk` (`MerchUdf5`).
- Fix: in both resolvers read the authenticated hint (`udf5` / `MerchUdf5`) first: if it has the right shape, `*_attempt_ref_matches_order(ref, hint)` holds and that order exists, return it; only then fall back to the exact match. Also refuse client-chosen track ids matching `/A[1-9][0-9]*$/` at `api.php:673` (or mint ids on the server). Add a regression to `test:knet` and `test:tpay`.
- Proof: the verifier ran the real `knet_resolve_track`, `knet_attempt_ref_matches_order` and `knet_attempt_ref` against sqlite; output "reference sent to bank: VICTIMTRACK123456A2 ... SETTLES THE WRONG ORDER (attacker's)" (`resolve_proof.php` in the scan scratchpad). The T-Pay callback was not re-read in full beyond the resolver.
- Why medium: needs the victim's order id (on the result page, URL, mail, warehouse mail), an equal total and a second attempt.

**M2 · auth-1 · Admin sign-out does not end other sessions, contrary to the code comment and `NATIVE-BACKEND.md`**
- Where: `admin.php:76-88` (logout route), `store.php:1135-1148` (`store_session_end`), `store.php:1166` (`store_admin_fingerprint`), `store.php:1205-1228`. WIP file: yes (admin.php, store.php), not at these lines.
- Found by: auth. Verifier: confirmed, **medium**.
- Scenario: logout destroys only the caller's session file. Every other session is validated against a fingerprint of `password_hash`, `totp_enabled` and `totp_secret`, which logout does not touch, so a copied cookie or a second browser stays valid up to 30 days (7 idle). There is no session list or revoke. Only a password reset or an authenticator change revokes.
- Fix: add a per-admin session epoch (for example `admin_users.session_epoch`) into the fingerprint, bumped on logout or on a separate "sign out everywhere". At minimum correct `store.php:975-976` and `NATIVE-BACKEND.md:265-266`.
- Proof: the logout path calls `store_session_resume()` then `store_session_end()` only; the fingerprint inputs are those three columns; the documentation wording contradicts it.

**M3 · money-5 · `order_items.name_en/name_ar` is varchar(120) but products accept 160 characters; such an order fails with HTTP 500 under strict SQL mode**
- Where: `admin.php:1478-1479` (`store_text(..., 1, 160)`), `store.php:3029-3030` (name copied untruncated), `api.php:896-900` (insert), `itemname.mysql.sql:22-23` and `schema.mysql.sql:693-694` (varchar(120)); `schema.mysql.sql:18-19` (`products.name_*` varchar(160)). WIP file: yes (admin.php, store.php), not at these lines.
- Found by: money. Verifier: confirmed, **medium**.
- Scenario: the owner saves a product whose English or Arabic name is 121 to 160 characters (Arabic counts by character). Every order containing it throws "Data too long" (1406) in the order transaction; the catch at `api.php:990-992` rolls back and answers `{error:'failed'}` 500, indistinguishable from an outage. The seed has no name over 90 characters.
- Fix: `mb_substr(..., 0, 120)` when snapshotting at `store.php:3029-3030`, and either cap product names at 120 in `product_save` or widen the two `order_items` columns to 160 in a migration (widening keeps history and catalogue agreeing).
- Proof: read-only. No truncation on the path; the PDO options (`store.php:55-65`) set no `sql_mode`; MariaDB 10.2.4 and later defaults to strict. Open point: the live `sql_mode` was not observed (see section 4).

### 3.2 Low (22)

**L1 · money-4 · KNET availability ignores `knet_via_cbk`**
- Where: `store.php:2070-2119` (`store_payment_config_ready` / `store_gateway_ready`), `api.php:261` and `692-693`, `php-knet/pay.php:9-31`, `admin.php:932-968`. WIP file: yes (store.php). Found by: money. Verifier: confirmed, **low** (reported medium).
- Scenario: (a) with the switch on and no Tranportal credentials, `store_gateway_ready('knet')` still demands Tranportal id, password and key, so KNET is dropped from `checkout_config` and the order route answers `payment_method_unavailable`: the documented one-setup mode cannot be used. (b) With the switch on and old Tranportal credentials present but the CBK config broken after switch-on (readiness is checked only at switch-on), KNET stays offered, the order, stock claim and fulfilment row are created, then `/knet/pay.php` 302s to `/pay/pay.php`, which answers 503/502.
- Fix: in `store_payment_config_ready` / `store_gateway_ready`, when the method is `knet` and the tpay config has `knet_via_cbk`, evaluate readiness against the CBK config (`cbk_assert_payment_config` plus ClientId, ClientSecret, ENCRP_KEY). Add a `test:knet-via-cbk` case with no Tranportal credentials.
- Proof: `knet_via_cbk` is read only by `pay.php`, `cbk.php` and the admin switch, never by `store.php` or `api.php`; `scripts/knet-via-cbk-test.mjs` does not cover checkout availability.
- Note: becomes a medium if the pending "merge T-Pay into KNET" release ships first, because (a) is then the normal state. The switch is OFF by default and not live today.

**L2 · money-2 · A second CAPTURED payment for an already-paid order is swallowed as `already_paid`, with no record, flag or alert**
- Where: `php-knet/callback.php:183-186`, `php-cbk/callback.php:326-329` (the locked selects at `callback.php:160-163` / `:321` do not read `cbk_paymentid`). WIP file: no. Found by: money. Verifier: confirmed, **low** (reported medium).
- Scenario: both gateways give each start a distinct bank reference (A1, A2) and allow restarts while pending, so a double tap or two tabs can complete two payments. The second capture hits the branch, rolls back, writes nothing (no `admin_activity_log`, no review state, no mail) and shows the customer success. Only a `callback.received` line in the payment log file shows it. A bank retry of the same callback cannot be told apart because the stored payment id is never compared.
- Fix: select `cbk_paymentid` in the locked read; in the paid-replay branch, when the new result is a valid capture with a different payment id, write a durable marker without changing `payment_status` (a `store_system_event('duplicate_capture_<track>')` plus a note such as `cbk_message='DUPLICATE_CAPTURE <paymentid>'`) so it shows in /backends Activity. Same for the T-Pay callback (compare `PaymentId`).
- Proof: read of both callbacks, the attempt-reference code and `pay.php:91`; the bank still holds both captures, so money is not lost, the shop just does not see it.

**L3 · money-3 · A cancelled order in payment_status `review` never releases its stock or discount use**
- Where: `store.php:2578-2597` (`$eligible` / `$dead` exclude `paid` and `review`), `cron-stock.php:98` and `:110`, `admin.php` fulfilment route (about 1165-1262) and `card_settled` (about 1335). WIP file: yes (store.php, admin.php, cron-stock.php). Found by: money. Verifier: confirmed, **low** (reported medium).
- Scenario: KNET and T-Pay park a payment in `review` (amount mismatch, missing payment id, unrecognised bank result, wrong method) with stock still claimed. The owner can mark such an order `cancelled` (not paid, not shipped), after which neither `store_stock_release` nor the sweeper touches it, and `card_settled` refuses a cancelled order. If the owner refunds at the bank, the garments stay claimed and a single-use code stays spent for ever; only `inventory_adjust` fixes stock, and nothing fixes the code use.
- Fix: treat (`payment_status='review'` and `fulfilment_status='cancelled'`) as releasable in `store_stock_release`, in `$dead` and in the two `cron-stock.php` clauses, or add an admin `review_resolve` route (refunded to failed) that runs under the row lock and calls `store_stock_release` and `store_discount_release`. Keep `review` excluded when the order is not cancelled. The exclusion itself is deliberate (money may be captured).
- Proof: traced the cancel, release, sweeper and settle paths; no route moves `review` to anything but `paid`. Needs a rare state plus a deliberate owner action; manual stock workaround exists.

**L4 · money-6 · No deadlock or lock-wait retry on the money path; opposite lock order between checkout and reinstate**
- Where: `api.php:~909-922` (discounts then `product_variants` in cart order), `store.php:2425-2461` (`store_stock_claim`), `store.php:2666-2697` (`store_order_reclaim`: variants then discounts), `php-knet/callback.php:303-311`, `php-cbk/callback.php:~409`. WIP file: yes (store.php). Found by: money. Verifier: confirmed, **low** (reported medium).
- Scenario: two checkouts whose carts share two variants in opposite order can deadlock; InnoDB aborts one with 1213 and the shopper gets a 500 and must retry (rolled back cleanly, no corruption). A reinstate racing a checkout that uses the same code and variant can deadlock the other way. A callback that hit 1205/1213 degrades to `review`/`database_write_failed` with money captured (the verifier could not construct a deadlock for the callback itself; the documented lock-wait source, mail under the order lock, is addressed by the WIP in U1).
- Fix: sort `$lines` by (slug, size) before `store_stock_claim`; claim discounts before stock in `store_order_reclaim`; add `order by` to the joined multi-row UPDATE in `store_stock_release`; bounded retry (2 to 3 tries, 50 to 200 ms backoff) on SQLSTATE 40001 / errno 1213 around the order transaction.
- Proof: `grep` for 1213/1205/deadlock in `dropin/` finds only a comment; lock order read in both functions. Not reproduced (no MariaDB).

**L5 · injection-3 + auth-10 + money-7 · KNET `pay.php` and `callback.php` have no rate limit and append attacker-sized lines to an unrotated payment log**
- Where: `php-knet/callback.php:26` (`callback.error_url`, 5 fields of 200 characters), `:42-44` (`callback.decrypt_failed`, 4,096 bytes of `trandata`), `php-knet/pay.php:66-77` (`pay.reject`), `php-knet/knet.php:187-203` (`knet_log`, `FILE_APPEND|LOCK_EX`, no cap or rotation). Compare `php-cbk/callback.php:17-19` (30 per minute) and `cbk_rate_hit`. WIP file: no.
- Found by: injection, auth and money (three lenses, one defect). Verifier: confirmed in all three, **low** (each reported medium).
- Scenario: an anonymous POST or GET with junk `trandata` makes `knet_decrypt` throw (no key needed) and appends a line of about 4.2 KB. About 2.5 million requests fill 10 GB; the VPS disk was 200 GB with 119 GB free (`VPS-SCAN-2026-10-31.md:347`). If the log shares a volume with `/var/lib/sporta/admin-sessions` and `tts-cache`, a full disk breaks sign-in and the voice cache. A flood also buries genuine bank evidence in the same file. Weakened by the verifiers: the 8,192-byte `callback.received` line is not anonymously reachable (it needs a valid decrypt); lines with non-UTF-8 payload collapse to a bare newline; the `pay_attempt` bump needs the victim's track id and is negligible; the "same volume" claim is unverified.
- Fix (cap and rotation first, since per-IP limits do not stop IPv6 rotation): log a hash and length of undecryptable input instead of 4 KB raw; size-cap or rotate `knet-payments.log` and `cbk` logs (logrotate or a size check inside `knet_log` / `cbk_log`); add a `knet_rate_hit()` twin of `cbk_rate_hit` through `sporta_rate_limit_hit` on the failure paths only (`decrypt_failed`, `error_url`, `pay.reject`), never on a genuine bank callback; optionally cap `pay_attempt` at 10 as CBK does.
- Proof: `grep` for rate limits in `php-knet/` finds none; `knet_decrypt` throws on non-hex or failed decrypt; no rotation found anywhere in the repo.

**L6 · injection-1 + auth-9 · Gateway and return-URL allowlists use `parse_url`, which disagrees with browsers on a backslash**
- Where: `admin.php:733-749` (the `$url` closure and `sportaUrl` variants; stored verbatim), `php-knet/knet.php:106-130` (`knet_assert_payment_config`), `php-cbk/cbk.php:91`, sinks `php-knet/pay.php:186`, `php-knet/callback.php:142`, `php-cbk/callback.php:125-273`. WIP file: yes (admin.php), not at these lines.
- Found by: injection and auth. Verifier: confirmed in both, **low** (injection reported medium, auth reported low).
- Scenario: a signed-in admin (or a stolen admin session) saves `production_url = https://evil.example\@kpay.com.kw/kpg/PaymentHTTP.htm`. PHP reads host `kpay.com.kw` (userinfo `evil.example\`), so the admin allowlist and the runtime host and path checks both pass. Browsers treat the backslash as a slash, so the KNET 302 from `pay.php:186` goes to `evil.example` with `tranportalId` and encrypted `trandata` in the query (trandata cannot be decrypted without the resource key). The same trick passes the `www.sporta.com.kw` check used for `response_url`, `error_url`, `return_url`, `result_page_url`, giving an open redirect after payment. libcurl 8.5 parses like PHP, so the server-side CBK calls are not affected.
- Fix: replace `parse_url` with one strict matcher: exact `^https://(kpay|kpaytest)\.com\.kw/kpg/PaymentHTTP\.htm$` for KNET, `^https://www\.sporta\.com\.kw(/[A-Za-z0-9/_.-]*)?$` for Sporta URLs; reject backslash, `@`, control characters, port, userinfo, query and fragment; store the rebuilt URL. Apply in `admin.php`, `knet_assert_payment_config()` and `cbk_assert_payment_config()` so a hand-edited config file is covered too.
- Proof: `parse_url('https://evil.example\@kpay.com.kw/kpg/PaymentHTTP.htm')` returns scheme https, host `kpay.com.kw`, user `evil.example\`, path `/kpg/PaymentHTTP.htm`; the real `knet_assert_payment_config` was run on it and passed. The browser step is the WHATWG rule, not run here. Low because it needs an admin who can already change credentials and prices.

**L7 · injection-2 · T-Pay runtime config check has no CBK host allowlist**

**L8 · injection-4 · Unauthenticated `ErrorCode` is written unbounded into `orders.cbk_message` and the log**
- Where: `php-cbk/callback.php:37-38` and `:119-121` (`cbk_note_gateway_error`, `callback.php:294-309`), `:70-71` (log), `:123` (echoed in redirect). WIP file: no.
- Found by: injection. Verifier: confirmed, **low**.
- Scenario: `GET/POST /pay/callback.php?ErrorCode=<text>&PayTrackID=<track of a pending order>` stores `<ErrorCode> Unknown gateway error` into `cbk_message` on that pending order (at most about 200 characters survive the varchar(200) column under strict mode; longer values throw and only log). The attacker needs a known track id and a still-pending order. Worse than the comment admits (the code comment calls the worst case "a note on a row it already knew"): a POSTed value is bounded only by `post_max_size`, goes whole into the `callback.gateway_error` log line before any track check, and is echoed rawurlencoded in the redirect `reason`. The rate limit (30 per minute) fails open when the DB is down.

- Proof: reading plus a PHP run of the same string expression; prepared statement, so no injection; `json_encode` prevents log-line injection.

**L9 · auth-2 · Anyone with the admin address can keep the admin's password-reset mail from working**
- Where: `admin.php:172-191` (limits), `:203` (early reply), `:218-219` and `:267-280` (mail, then revoke older tokens); `config-path.php:175-188` (fixed-window limiter). WIP file: yes (admin.php). Found by: auth. Verifier: confirmed, **low** (reported medium).
- Scenario: `forgot_password` is unauthenticated and needs only the `X-Sporta-Admin: 1` header. The per-address budget is 3 mails per 30 minutes; once spent the reply is the same `{ok:true}` but nothing is sent. A stranger who knows the admin login address spends the budget from one IP (8 per 15 minutes per client allows 3 per window) so the owner's own request is silently suppressed; each delivered mail also kills all older unused tokens, so a link just received dies when a newer one is delivered. Whether the admin address is guessable is not shown by the code (`store_admin_recovery_sender` selects the sender, not the admin address). The first three mails do reach the owner's inbox.
- Fix: do not revoke older unexpired tokens when a new one is mailed (or reuse the live token); keep a floor of one mail per window for the owner; keep the per-client limit as the main brake.
- Proof: read of the full route; no runtime run.

**L11 · auth-6 · Customer password-reset request revokes the earlier link before the new mail is sent**

**L12 · auth-3 · Phone-keyed order controls let anyone block a victim's phone number**
- Where: `store.php:692-709` (phone cooldown), `store.php:585-597` and `:531` (`STORE_COD_OPEN_MAX = 3`), `api.php:757-771`, `:849`. WIP file: yes (store.php). Found by: auth. Verifier: confirmed, **low**.

## 8. Claims in docs and comments that the code contradicts

1. **Sign-out ends every session.** `store.php:975-976` and `NATIVE-BACKEND.md:265-266` say sign-out, a password reset or an authenticator change ends every session at once. Only the last two do; sign-out destroys the caller's own session file (M2).
2. **"One a minute per client and per phone" (`CLAUDE.md`, `order_cooldown_seconds`).** The phone half is exact only for COD (phone advisory lock). Concurrent card orders from two clients can both pass (L13). The code comment at `api.php:852-854` concedes this; the project doc does not.
3. **KNET through the CBK gateway needs only the T-Pay credentials (`CLAUDE.md`, "One-setup option" and the pending merge decision).** `store_gateway_ready('knet')` still demands Tranportal id, password and 16-byte key before KNET is offered at checkout, so the mode is unusable without them (L1).
4. **`cbk/callback.php` comment: the worst an unsigned `ErrorCode` return can do is "a note on a row it already knew".** The note text is attacker-chosen (about 200 characters, pending orders), and the unbounded value is also logged and echoed in the redirect (L8). The same file's comment that track ids are not secrets sits beside resolvers that let a browser-chosen id outrank the bank-signed `udf5` hint (M1).
5. **`api.php` comments beside `'brand_logo' => null` / `'slide_image' => null`: a cold cache of five slides would trip any sane ceiling.** A bucket of about 300 per minute would not be tripped by five requests (L20).
6. **`cron-fulfilment.php` (at `a2ea548e`): "a mail is one sendmail call, so the wait is short".** `mail()` has no timeout; superseded by the rewrite in HEAD (U1).
7. **Secrets documentation (`CHECKOUT-SECRETS.md:71,193`, `NATIVE-BACKEND.md:59`): `cron_key` is 32 or more random characters.** No code check enforces a length or refuses a short key; `config.example.php` ships it empty (L15).
